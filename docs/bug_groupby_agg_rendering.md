# 缺陷：groupby 聚合语义在渲染时丢失，findings 把「计数」伪装成「ID」

**报告人**：Claude Code（第 7 节评审过程中发现）
**日期**：2026-08-25
**严重度**：高。**污染的是 findings 本身**，judge 与人工标注者读的是同一份 findings（`src/eval/metrics.py:365` 的 docstring 明确保证 byte-for-byte 相同），因此**两侧同时受害**，且无法靠调 judge 配置绕过。
**状态**：未修复。本文件为诊断与复现，**未改动任何代码，未提交**。

---

## 1. 现象

`pandas_groupby` 做 `count` 聚合时，结果列沿用**源列名**。当源列是 `order_id` 时，计数结果渲染成 `order_id=2527`，字面读是「订单号是 2527」，而真实含义是「有 2527 笔订单」。

聚合函数本身（`agg_func`）在 `pandas_tool` 的返回边界上被丢弃，渲染层拿不到任何可以消歧的信息。

## 2. 最小复现

```python
import pandas as pd, sys
sys.path.insert(0, '.')
from src.tools.stats_tool import pandas_tool
from src.eval.metrics import render_findings

df = pd.DataFrame({
    "order_id": range(1, 11),
    "quarter":  [1, 4, 4, 3, 3, 2, 3, 1, 3, 2],
    "revenue":  [10] * 10,
})
out = pandas_tool(
    df,
    {"operation": "groupby", "group_by": "quarter",
     "agg_col": "order_id", "agg_func": "count"},
    {},
)
print(out["result_summary"])
print(sorted(out.keys()))
print(render_findings([{
    "method": "count_orders_per_quarter",
    "result_summary": out["result_summary"],
    "result": out["result"],
}]))
```

实际输出：

```
pandas/groupby → 4 rows. Top results: quarter=3, order_id=4; quarter=1, order_id=2; quarter=2, order_id=2; quarter=4, order_id=2
['result', 'result_df', 'result_summary', 'warnings']          <- agg_func 不在其中

[count_orders_per_quarter] pandas/groupby → 4 rows. Top results: quarter=3, order_id=4; ...
    full result: [{'quarter': 3, 'order_id': 4}, {'quarter': 1, 'order_id': 2}, ...]
```

`quarter=3, order_id=4` 的真实含义是「Q3 有 4 笔订单」，但渲染结果和「Q3 的订单号是 4」在文本上完全无法区分。

## 3. 代码路径

| 位置 | 问题 |
|---|---|
| `src/tools/stats_tool.py:408` | `df.groupby(group_by)[agg_col].agg(func).reset_index()` —— 聚合列沿用源列名，`count` 后仍叫 `order_id` |
| `src/tools/stats_tool.py:415-418` | `pandas_groupby` 返回 `{"result", "result_df", "n_groups", "agg_func"}`，**`agg_func` 此处仍在** |
| `src/tools/stats_tool.py:641-645` | `pandas_tool` 只透传 `result` / `result_df` / `result_summary` / `warnings`，**`agg_func` 与 `n_groups` 在此丢弃** |
| `src/tools/stats_tool.py:633-638` | `result_summary` 由 `rows[:5]` 直接 `f"{k}={v}"` 拼接，无聚合语义 |
| `src/eval/metrics.py:378` | `render_findings` 渲染 `full result`，同样只有裸记录 |

## 4. 真实影响：calibration20 的 C08

`data/annotations/dmxapi_calibration20_nonpredictive_blind_relabel.html` 中 C08（盲编号 R09），findings 第三步：

```
[count_orders_per_quarter] pandas/groupby → 2 rows.
    full result: [{'quarter': 1, 'order_id': 2419}, {'quarter': 4, 'order_id': 2527}]
```

**2419 + 2527 = 4946**，与上一步 `filter_quarters` 的行数精确相等，可确证这两个数是计数。

GPT-5.6 Sol 在该 case 上把 `Q4 2024 had 2,527 orders` 判为 `no evidence found`，20 条 claim 里判了 13 条 unsupported，groundedness = 0.300；人工给 0.75。**这是全部 20 条里分歧最大的 case 之一。**

判官照字面读 `order_id=2527` 并拒绝将其当作计数，**在给定渲染文本的前提下是可辩护的**。也就是说这条分歧的一部分不是判官过严，而是它拿到的证据文本本身有歧义。

同一 case 还暴露了一个相关但独立的问题：报告称 `The highest revenue in Q3 was generated by order_id 1 at $1,822.28`。findings 中 order_id=1 确为 1822.28，但那只是 10,000 行结果被 `_STEP_RESULT_CAP = 1500`（`src/eval/metrics.py:345`）截断后的**头几行预览**，不是最大值。**报告是从截断预览里编出了「最高」**，判官标它 unsupported 是对的，而人工漏判了。

## 5. 影响范围

- **不限于 `count`**：`sum` / `mean` 同样丢失聚合函数。`revenue` 求和后仍叫 `revenue`，「总收入」与「平均收入」在文本上无法区分。`count` 只是最刺眼的一种，因为它让**列名与量纲彻底错配**。
- **不限于 eval**：`render_findings` 供 judge 与人工标注共用，`result_summary` 还流向 `src/agents/viz_agent.py:173` 与 `:229`。**报告生成侧也在读同一份有歧义的文本**，所以报告自身误读 findings 的风险同源。
- **阶段 4 的连带后果**：任何依赖 groupby 计数的 case，其 groundedness 人工标签与机器分**都建立在有歧义的证据上**。这不是重跑 judge 能修的，重跑前必须先修渲染。

## 6. 建议修法（未实施，交由 owner 裁定）

最小改动，按优先级：

1. **`pandas_groupby` 给聚合列改名**：`count` → `{agg_col}_count`（或统一 `n_rows`），`sum` → `{agg_col}_sum`，依此类推。这一处改完，`order_id=2527` 变成 `order_id_count=2527`，歧义直接消失。
2. **`pandas_tool` 透传 `agg_func` 与 `n_groups`**（`stats_tool.py:641`），让下游有能力自行消歧。
3. **`result_summary` 带上聚合语义**：`pandas/groupby(count of order_id by quarter) → 2 rows. ...`

**注意向后兼容**：改列名会影响 `src/tools/chart_tool.py:156`（按 groupby 结果推断图表）与任何按列名取值的下游。改之前建议先跑一遍现有 case，确认没有硬编码 `agg_col` 名的消费者。

## 7. 对已有产物的处置建议

**不建议**因此重跑 calibration20 的人工标注。更省的做法：把受影响的 case 挑出来（findings 中含 `pandas/groupby` 且 `agg_func=count` 的），在第 7 节评审要求的 claim-level 人工裁决里**优先纳入 C08**，确认修复后这条分歧是否消失，再决定是否有必要扩大重跑范围。

相关裁定见 `docs/handoff_maeda_to_subsystems.md` 第 8.3、8.6(d)、8.7 的 Q9。
